2. Initial Understanding
PitchGrader is a full pipeline, not just an API. Scrapers pull raw Statcast/MLB pitch data into SQLite, a trained model scores every pitch's shape into a "Stuff+" grade, an aggregation layer rolls that into pitcher cards and leaderboards, and a Flask app serves it all, including a clean frontend.

3. Repository Organization
Clean module boundaries that match architecture.md exactly: scraper/ and live/ for ingestion, features/ for shape engineering, model/ for the model itself, profiles/ for aggregation, storage/ for the override table, app.py for the web layer, tests/ and docs/ for verification. Dependencies are pinned properly as well.

4. README and Run Instructions
The README documents every main.py subcommand (train / score / profiles / live), the Flask serve command, and a test-install path. I ran it rather than just reading it. pip install -r requirements-dev.txt then pytest tests/ worked with no changes needed, and passed 15/15, exactly matching what the docs claim.

5. Architecture and Implementation Alignment
architecture.md holds up well against the code. The "model boundary" claim, that model/ owns its own artifacts and everything else just calls predict(), is real. model/artifacts/ contains exactly the files the doc says should be committed (ensemble_all.pkl, movement baselines, cutter router, norm files), and nothing outside model/ reaches into model internals.





One thing the doc doesn't mention at all: the admin surface. app.py has four /api/admin/* POST routes (rebuild-all, retrain, rebuild-season, rescore-spring) that can drop database tables and kick off full retrains. None of that is described in architecture.md.

6. Testing and Verification Evidence
I ran the suite myself, and 15 passed, matching both docs/ai-implementation-review.md and docs/manual-verification.md exactly. The split is deliberate and well-designed: pure-function tests (test_prob_resid.py) need no trained model and run in about a second, and behavioral tests (test_predict.py) load ensemble_all.pkl and skip automatically if it's missing, so the suite still passes on a checkout with no model trained. Unlike the sibling repo, nothing here needed a fix to run.

 

I didn't run the full train/score pipeline end-to-end. data/statcast.db isn't present locally by design, so that part is unverified by me. The manual-verification doc's claims are the only evidence there.

7. AI-Assisted Engineering Evidence
This is the strongest doc in the repo. It doesn't just say "AI helped write tests," it names a specific test that was generated, found to be flaky, and revised. The first velocity test asserted monotonicity on the composite xRV, which folds in a deliberately noisy contact grid, so it was split into two sharper tests (one on the swing head's raw P(whiff), one on a wide velocity gap), with the reasoning spelled out.

9. Engineering Strengths
The AI-assisted-engineering doc reasons about why a generated test was revised, pointing at a specific noisy component (the contact grid) and showing the sharper replacement, not just claiming AI review happened. Pitch-type overrides persist in their own table (storage/overrides.py) and get re-applied on every re-score, as the raw pitches_table gets overwritten wholesale on every re-scrape. Without that, every manual correction would be silently wiped on the next scrape.

 

10. Recommendations or Engineering Questions
Hardcoded fallback admin token. app.py has: _ADMIN_TOKEN = os.environ.get("ADMIN_TOKEN", "stuffplus-admin-2026"). If the ADMIN_TOKEN env var isn't set on the live Railway deployment, the admin routes, which can drop scored tables and trigger full retrains/rebuilds, are protected by a token sitting in plaintext in a public GitHub repo. This should fail closed when the env var is unset, not fall back to a known default. Delete the two stray backup files (model/train.py.bak, templates/player.html.darkbak) or add them to .gitignore. Right now they're just dead weight, and the .darkbak one is a near-full duplicate of a 60KB template. 

11. Highest-Priority Recommendation
Fix the admin-token fallback. It's a live, publicly deployed app where the routes with the largest blast radius (drop tables, trigger retrains) are gated by a secret that's committed to source and actually used as a fallback, not just sitting there as a placeholder.
